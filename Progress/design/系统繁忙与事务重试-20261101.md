# 系统繁忙与事务重试 · 2026-11-01

开工备份819fe45已推送。用户报告旧1.8投稿偶发多次“系统繁忙”，不记得具体时间；要求检查是否限制过严，并评估新增点赞／投票的影响。

## 已确认与未确认

旧checkWeeklyCode将事务异常统一返回“系统繁忙，提交失败”，不能据此判定限流。投稿、点赞、投票原来使用手动事务，代码没有在明确写冲突时自动重试。线上打包SDK的runTransaction有事务冲突重试，手动startTransaction没有。三个函数都是3秒超时。

用户提供的最近24小时日志截图中，所示完成报告约625—1312ms，状态200；202为冷启动初始化记录，可按相同请求ID关联后续完成报告。200只证明函数正常返回，也可能返回success:false；这些行不足以证明此前业务提交成功或失败，更不能证明历史故障全部来自事务冲突。没有定位到用户当时的具体错误，不把推测写成根因。当前没有超时证据，未更改超时、实例并发或云服务配额。

## 修复

- 三个包采用相同有限策略：仅明确数据库事务冲突才回滚、短暂退避、启动新事务并重新读取，最多总共3次；两次等待40／80ms，各加小于30ms随机抖动。SDK错误码和明确冲突消息可识别，未知数字错误码不猜测含义。安全检查置于事务外，不因重试重复调用。
- 业务版本冲突、权限、验证码、频率限制不自动重放；管理员必须刷新后评估新状态，不能把旧revision自动替换为新revision。
- 不对网络超时或确认响应丢失盲目重放写入。这种情况下服务端可能已保存；新版首页先同步本人记录，保留填写内容。同一用户同一周期重发完全相同的清洗后歌名／歌手／备注，返回“已收到”，不新增投稿、不累加计数；不同内容仍拒绝第二次提交。
- 投稿与周计数从原先分步更新改为同一事务提交。先读取固定周计数文档，再做同名和候选检查，提交时更新同一文档，使并发投稿发生可检测的写冲突并重读最新状态；索引和每周唯一规则保持。精简判重查询返回字段。SDK的count封装会检查错误，底层count不携带事务ID，不能单靠count当事务锁。
- 未确认结果返回SUBMISSION_UNCERTAIN，冲突重试耗尽返回SUBMISSION_BUSY；点赞／投票的冲突重试耗尽显示具体稍后重试提示。投稿日志只记可公开错误码和冲突类别，不输出用户正文、身份或查询语句。

## 各类限制的结论

| 场景 | 保留的行为 | 本轮处理 |
| --- | --- | --- |
| 点歌 | 每人每周一次、同名判重；前250条pending，之后overflow仍保存并计数 | 修复明确冲突恢复及投稿／计数原子性，不扩大候选池 |
| 点赞 | 多首可赞、可取消；同人同曲一份有效关系，三期可互动 | 个人关系与歌单汇总仍同事务，冲突后重读，不重复累计 |
| 投票 | 每个话题一人一票，截止前可改票 | 冲突后重读投票及汇总；截止／隐藏／删除校验不放宽 |
| 使用反馈 | 每分钟1条、每天3条 | 明确业务RATE_LIMIT，保持防刷，不归为系统繁忙 |
| 管理员操作 | revision、角色、验证失败锁定 | 保持明确刷新／权限提示，禁止自动覆盖别人编辑 |

点赞和投票使用各自的个人关系与汇总数据，不占用投稿的周计数或250名额；仍共享云开发资源，不能承诺新增请求毫无负载。没有在正式数据上压测，也未以模拟测试推导线上最大吞吐。现在的数据规模暂不引入队列、分片计数或扩大实例；后续若出现3秒超时或持续冲突，依据具体错误码／时延再调整。
